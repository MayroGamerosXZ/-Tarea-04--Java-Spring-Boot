1. Resumen Ejecutivo del Sistema

ThunderMax es una API RESTful diseñada específicamente para resolver las necesidades operativas de una ferretería guatemalteca. A diferencia de un sistema de inventario genérico, ThunderMax implementa un motor de Kárdex (bitácora de movimientos) estricto. El stock de los productos no se altera manualmente, asegurando que cada incremento (compras a proveedores) o decremento (ventas a clientes) quede auditado.

2. Arquitectura de Software

El sistema abandona el enfoque de scripts sueltos y adopta una arquitectura de N-Capas utilizando el framework Spring Boot de Java. La transición de tecnologías como Node.js hacia Java Enterprise obliga a una separación de responsabilidades más formal:

  • Capa de Presentación (Controllers): Anotados con @RestController. Se encargan exclusivamente de recibir peticiones HTTP, delegar validaciones iniciales (con @Valid) y retornar respuestas HTTP (200, 201, 204).
  • Capa de Servicio (Business Logic): Anotados con @Service. Aquí reside el "cerebro" de la ferretería. Validaciones complejas (ej. revisar si hay suficiente pintura para vender) ocurren aquí.
  • Capa de Acceso a Datos (Repositories): Interfaces que heredan de JpaRepository. Permiten consultar PostgreSQL sin escribir sentencias SQL manuales mediante el uso de Hibernate/ORM.
  • Capa de Transferencia (DTOs): Objetos inmutables (usando Records de Java 21) que filtran la información. Un cliente que consulta un producto no necesita ver campos técnicos de auditoría, por lo que el DTO actúa como escudo.

4. Descripción de Módulos Core

A. Módulo de Inventario y Kárdex Inteligente

Implementa el patrón de "Fuente Única de Verdad". El controlador prohíbe explícitamente enviar actualizaciones del campo stock mediante peticiones PUT. Todo abastecimiento debe pasar por el InventarioService.registrarEntrada(), el cual incrementa el inventario, calcula costos totales e inyecta un asiento de tipo ENTRADA en el Kárdex.

B. Módulo de Cotizaciones a Ventas (Transaccional)

Una característica sobresaliente es la "Magia" de conversión. El endpoint /api/cotizaciones/{id}/convertir-venta transforma una proforma en una factura real en milisegundos. Esta operación está envuelta en una transacción @Transactional: si el cliente cotizó 10 bolsas de cemento hace una semana, pero hoy al convertirla solo quedan 5, el sistema detecta la anomalía, rechaza la operación y deshace (rollback) cualquier cambio parcial.

C. Calculadora de Materiales (Valor Agregado)

Módulo de utilidad de ferretería. Aplica algoritmos físicos simples (rendimiento de metros cuadrados por galón de pintura o bolsa de cemento) para sugerir cantidades. Posteriormente, cruza este dato dinámicamente con la base de datos para sugerirle al cliente únicamente los productos de los cuales hay stock suficiente.

5. Reflexión de Aprendizaje y Resolución de Problemas (Post-Mortem)

¿Qué aprendí o reforcé?

El mayor refuerzo fue comprender la robustez del tipado estricto y la Inyección de Dependencias. Viniendo de ecosistemas como Node.js (Express), donde uno debe enlazar a mano las rutas con los controladores, Spring Boot me demostró que el uso de anotaciones (@Autowired, @RestController) automatiza la creación de componentes. Aprendí a delegar el trabajo pesado de base de datos a JPA (Hibernate) en lugar de escribir consultas crudas o armar ORMs desde cero.

¿Qué fue lo más interesante?

Sin duda, la anotación @Transactional. En un proyecto básico de Node.js, si ocurre un error a la mitad de un ciclo for mientras descuento 10 productos, los primeros 5 quedan descontados y la base de datos queda corrupta. Con Spring Boot, aprendí que esta simple anotación asegura el principio ACID: o se guarda toda la factura y sus detalles, o no se guarda absolutamente nada.

¿Qué NO sabía cómo funcionaba y ahora tengo bien claro? (El caso del Error 500 y Lazy Loading)

Al finalizar el proyecto, me topé con un error interesante: El servidor arrojaba un código HTTP 500 al consultar los productos (LazyInitializationException). No entendía por qué, si el código estaba perfecto.

El Descubrimiento: Descubrí cómo maneja Hibernate las relaciones (Lazy Loading o Carga Perezosa). Para ahorrar RAM, Java no extrae la "Categoría" y el "Proveedor" de un Producto hasta que uno los pide explícitamente. Al intentar serializar el producto a JSON en el controlador, la sesión de base de datos ya se había cerrado.

La Solución: Comprendí el concepto de open-in-view. Al configurar spring.jpa.open-in-view=true en mi archivo application.properties, le ordené al framework que mantuviera viva la conexión a la base de datos hasta que el JSON terminara de renderizarse y enviarse al cliente (Swagger/Postman). Este problema no suele ocurrir en JavaScript porque todo se carga en objetos planos de memoria. Entender cómo gestiona las sesiones un lenguaje empresarial como Java me dio mucha claridad sobre el rendimiento de las bases de datos.
