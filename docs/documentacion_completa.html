1. Introducción y Objetivos del Proyecto

El proyecto ThunderMax nace como respuesta a la necesidad de modernizar la gestión operativa de una ferretería guatemalteca. El objetivo principal fue construir un sistema robusto en el backend que trascienda al típico CRUD básico y aplique reglas de negocio reales.

A diferencia de sistemas genéricos, ThunderMax garantiza la integridad de los datos implementando auditoría estricta de inventario a través de un "Kárdex" y forzando flujos transaccionales seguros (ACID) durante la facturación, además de brindar valor agregado como herramientas de cálculo de materiales constructivos.

2. Arquitectura de Software y N-Capas

Para asegurar que el sistema sea escalable y fácil de mantener, se aplicó una arquitectura de N-Capas fuertemente tipada utilizando el patrón MVC (Model-View-Controller) enfocado a API REST:

[AGREGAR AQUÍ: IMAGEN - Diagrama de la Arquitectura N-Capas (Controladores -> Servicios -> Repositorios -> BD)]
  • Capa de Controladores (Controllers): Utiliza @RestController. Se encarga de exponer los endpoints (ej. /api/ventas), deserializar los JSON entrantes, aplicar reglas de validación de sintaxis (@Valid, @NotNull) y delegar el proceso real a la capa de servicios.
  • Capa de Servicios (Business Logic): Anotada con @Service. Es el "cerebro" del sistema. Aquí se calculan los impuestos (12% de IVA en Guatemala), se valida la existencia de stock, y se gestiona la lógica de proformas.
  • Capa de Repositorios (Data Access): Implementa JpaRepository. Aísla toda la interacción con la base de datos PostgreSQL, utilizando Hibernate para traducir los objetos de Java a comandos SQL de forma transparente.
  • Manejo Global de Excepciones: Un componente @RestControllerAdvice intercepta cualquier error (como intentar vender material sin stock o buscar un producto que no existe) y devuelve un formato JSON de error estándar, evitando que el servidor colapse.

3. Stack Tecnológico Utilizado

La selección tecnológica del backend responde a estándares corporativos actuales de alta disponibilidad:

  • Java 21: Lenguaje principal (utilizando características modernas como los Records para los DTOs).
  • Spring Boot 3: Framework de inyección de dependencias y auto-configuración rápida.
  • PostgreSQL 17: Motor de base de datos relacional para garantizar la integridad de las transacciones (ejecutado sobre contenedores de Docker).
  • Spring Data JPA (Hibernate): ORM para el mapeo de tablas relacionales a clases de Java.
  • Postman y Swagger (OpenAPI 3): Herramientas utilizadas para pruebas de los endpoints REST, simulación de peticiones HTTP y validación de las estructuras JSON de respuesta.
  • Lombok: Librería que elimina el código repetitivo en Java (como los getters, setters y constructores) mediante anotaciones.

5. Lógica de Negocio y Módulos Principales

A. Inventario Auditado (Kárdex)

En ThunderMax, está prohibido técnicamente que el usuario modifique la columna stock de la tabla Productos manualmente. Para agregar mercancía, se debe realizar un proceso de "Entrada", el cual automáticamente inserta un registro tipo ENTRADA en la bitácora del Kárdex, subiendo el inventario. De la misma manera, anular una venta devuelve el inventario usando un registro tipo DEVOLUCION.

[AGREGAR AQUÍ: IMAGEN - Captura de Postman mostrando una "Venta" (Status 201 Created y JSON)]

B. El Poder de las Cotizaciones

Los vendedores pueden generar cotizaciones (proformas) que amparan un precio por ciertos días. Destaca el endpoint de "Conversión Mágica", el cual toma el ID de una cotización y la transforma en una Factura real. En este proceso, el servicio verifica en milisegundos si todavía hay stock suficiente para respetarle la cotización al cliente.

C. Calculadora de Herramientas y Reportes

Para acercarse al modelo real de una ferretería, se implementó una función matemática que, dados el "largo" y "ancho" de una superficie, calcula cuántos galones de pintura o bolsas de cemento se requieren, y hace una consulta dinámica a la BD para recomendar qué marcas están en stock actualmente.

D. Frontend Nativo Integrado (ERP & POS)

Como complemento al robusto backend, se construyó una interfaz de usuario HTML5/CSS3/JS que se conecta asíncronamente con la API. Este frontend destaca por:

  • Sincronización en Tiempo Real: Una función central (sincronizarSistema()) intercepta cada venta o ingreso, actualizando instantáneamente el Dashboard de KPIs sin recargar la página.
  • Auditoría de Kárdex: Permite realizar entradas de compra, registrar salidas manuales por merma, y consultar una bitácora detallada por producto que incluye el historial exacto de movimientos, costo unitario y precio de venta.

6. Reflexión de Aprendizaje y Resolución de Problemas

¿Qué aprendí o reforcé en esta transición?

Al venir de un ecosistema fuertemente ligado a JavaScript y Node.js, este proyecto reforzó brutalmente mis bases de Arquitectura de N-Capas y Tipado Estricto. En Spring Boot, el uso del contenedor de Inversión de Control (IoC) y las anotaciones automatizan la inyección de dependencias, obligando al desarrollador a ser disciplinado con la separación de responsabilidades y el uso de DTOs.

¿Qué fue lo más interesante?

El hallazgo más interesante fue descubrir cómo delegar la gestión del principio ACID a la base de datos a través de la anotación @Transactional. Si en el punto de venta el cliente compra múltiples productos y el sistema falla por falta de stock a la mitad del proceso, Spring Boot hace un rollback automático e instantáneo, protegiendo al sistema de sufrir corrupción de datos.

El Doble Error del API: Qué NO sabía cómo funcionaba y ahora tengo bien claro

Durante el desarrollo del punto de venta y catálogo, me topé con dos errores críticos de serialización que desconocía por completo cómo funcionaban a bajo nivel en Java:

  1. El Error 500 por Lazy Loading: El sistema colapsaba al leer productos porque Java, para ahorrar memoria RAM, desconecta la base de datos antes de traer llaves foráneas (Carga Perezosa). Lo solucioné configurando spring.jpa.open-in-view=true, comprendiendo el ciclo de vida de la conexión SQL vs las respuestas HTTP.
  2. El Colapso por Recursión Infinita (Stack Overflow): Al procesar una venta desde el Frontend, el navegador se quedaba "pasmado". Al revisar los logs, descubrí que una Venta contiene Detalles, y cada Detalle apunta de regreso a la Venta. Jackson (el conversor a JSON) entraba en un bucle infinito serializando uno dentro del otro hasta agotar la memoria. Lo solucioné magistralmente aprendiendo a usar la anotación @JsonIgnore en la relación hija, cortando el ciclo.
